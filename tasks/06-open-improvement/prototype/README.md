# Прототип мониторинга очереди обмена с 1С

Учебный скрипт к идее № 2. Он читает вымышленный JSON и печатает уведомления. К настоящей 1С, базе и чату не подключается, заказы не меняет и не удаляет.

Правила, по которым устроено решение, лежат в [monitoring-rules.md](monitoring-rules.md). Пороги демонстрационные: проверка раз в 5 минут, ожидание дольше 15 минут, больше 5 неудачных попыток, явная ошибка сразу. В компании их нужно согласовать.

Нужен PHP 8.1+. Запуск из этой папки.

## Проверка

```text
php tests/test-monitor.php
```

Тест пишет память уведомлений во временную папку и учебные JSON не меняет.

## Сценарии

Во всех командах момент проверки фиксирован, поэтому файлы не устаревают. `--state` — память уже отправленных проблем. Для чистого просмотра каждый раз указывайте новый файл, например `var/state.json`. Папка `var` создаётся при запуске и к учебным данным не относится, её можно удалить.

```text
php monitor.php --orders=data/ok.json --now=2026-10-22T12:00:00+03:00 --state=var/ok.json
php monitor.php --orders=data/incident.json --now=2026-10-22T12:00:00+03:00 --state=var/incident.json
php monitor.php --orders=data/incident.json --now=2026-10-22T12:00:00+03:00 --state=var/story.json
php monitor.php --orders=data/changed-error.json --now=2026-10-22T12:00:00+03:00 --state=var/story.json
php monitor.php --orders=data/incident.json --now=2026-10-22T12:00:00+03:00 --state=var/recover.json
php monitor.php --orders=data/recovered.json --now=2026-10-22T12:00:00+03:00 --state=var/recover.json
```

| Файл | Что видно при `--now=2026-10-22T12:00:00+03:00` |
|------|--------------------------------------------------|
| `data/ok.json` | Оба заказа уже переданы, уведомлений нет |
| `data/incident.json` | 5 минут ожидания молчит; 25 минут, контрагент, обрыв связи и 6 попыток дают уведомления |
| `data/changed-error.json` | Тот же набор, но у B2B-9104 ошибка сменилась на «Ошибка соединения». Новое сообщение будет, только если в `--state` ещё лежит старая причина |
| `data/recovered.json` | B2B-9104 уже передан. Сообщение о восстановлении будет, только если раньше по нему писали о проблеме |

Повтор той же команды с тем же `--state` новые уведомления не добавляет.

## Пример вывода

`data/incident.json`, первая проверка:

```text
[ОЖИДАНИЕ] Обмен с 1С
Заказ: B2B-9103
Причина: Ожидает передачи 25 минут, порог 15 минут
Попыток передачи: 1
Действие: Проверить, обрабатывается ли очередь обмена. Заказ не удалён.

[ОШИБКА] Обмен с 1С
Заказ: B2B-9104
Причина: Контрагент не найден
Попыток передачи: 3
Действие: Проверить карточку контрагента в 1С. Заказ не удалён и сам в 1С не отправлен.

[ОШИБКА] Обмен с 1С
Заказ: B2B-9105
Причина: Ошибка соединения
Попыток передачи: 2
Действие: Проверить доступность 1С. Заказ не удалён и сам в 1С не отправлен.

[ОШИБКА] Обмен с 1С
Заказ: B2B-9106
Причина: Неудачных попыток 6, порог 5
Попыток передачи: 6
Действие: Открыть журнал обмена и не повторять отправку вслепую. Заказ не удалён и сам в 1С не отправлен.

Итог: всего 6, передано 1, ожидает 3, проблемных 4
```

Если файл очереди не найден или JSON сломан, скрипт завершается с ошибкой и прямо пишет, что очередь не прочитана. Это не то же самое, что «проблемных 0».

## Ограничения учебной версии

Скрипт видит только тот JSON, который ему передали. Он не знает, остановил ли один заказ всю пачку, как в утреннем инциденте с контрагентом. Интервал 5 минут здесь записан как договорённость о расписании: сам скрипт по часам не запускается, его вызывает человек или будущий планировщик.

## Что нужно для настоящей очереди

Чтение статуса, попыток, времени и текста ошибки из базы, API или журнала, учётка только на просмотр. Запуск по расписанию. Тот же файл памяти, чтобы не слать одну причину каждые 5 минут. Доставка текста в корпоративный чат вместо консоли. Пороги утвердить до включения. Удаление заказа, смена статуса и пропуск строки в 1С в эту учётку не входят.
